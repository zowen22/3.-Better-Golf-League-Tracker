## 2026-08-21 — Score Entry: Sticky Header, Desktop Column-Fit, Skins Checkbox Column

*Status: `COMPLETED`*
*Type: `Manual`*

### What Was Done

**@user pulled up a saved copy of GolfLeagueTracker's own score-entry page (`Enter Scores.html`, downloaded via browser "Save As") mid-session as a concrete layout reference**, after describing several Score Entry (`enter_week.html`) complaints: a small visual "buffer" between the A and B rows of a pair, hole columns not lining up from one group's scorecard to the next, desktop layout putting a big dead gap between the name column and the hole grid instead of filling the window, and a request that the hole-number/par/hcp header rows stay pinned while scrolling.

**Removed the A/B row buffer**: it was the `sc-vs-row` divider — @user confirmed by inspection, not a CSS padding/margin issue. Removed it from the live-entry pairs loop only (group-to-group separation still comes from `.ew-matchup-block`'s own border); left the completed-scorecard view's equivalent divider alone since @user's complaint was about live entry specifically.

**Sticky header, done as native per-table sticky rather than a page-level restructure**: previously only the *first* matchup group's hole/par/hcp header rendered visibly (every later group's was a zero-height hidden duplicate, kept only so `table-layout:fixed` and the mobile column-fit script had something to measure) — a deliberate "one continuous spreadsheet" look. Investigated a single-shared-header restructure (would need `form="..."` attribute association instead of DOM nesting to let one `<table>` span every group's rows across independent `<form>` submits) but that's a much larger, riskier change; instead un-hid every group's header and made each individually `position: sticky`. Because the headers are identical in content, as one table's header scrolls out of range the next group's already-in-place header picks up the stick at the same screen position — reads as one continuous pinned header without the restructure. Offsets are computed in JS off `--nav-height` (existing CSS var, set by `base.html`) rather than hardcoded, so row-height/font changes can't desync it.

**Desktop column-fit (`ewFitDesktop()`, new, page-scoped to `enter_week.html`)**: root cause of the "big dead gap" was `table-layout: auto` + `width: 100%` with only `.sc-col-name` having a `min-width` — the browser was free to dump all leftover width into that one column. New function measures the worst-case name-column width across *every* scorecard on the page (temporarily switching to `table-layout: auto; width: auto` to let the browser compute it, then reading back `.sc-col-name`'s natural width — same technique the existing mobile `fit()` explicitly tried and rejected for iOS, but iOS's synchronous-reflow quirk documented there doesn't apply at desktop widths), then applies that one shared width plus a computed hole-column width (filling the remaining container width) to every table via `table-layout: fixed`. Result: hole columns line up vertically from one group to the next, and the table always fills the window. Also bumped desktop `.scorecard-table` font-size 13px → 14px to match GLT's own (Bootstrap's un-overridden body default). Made a small, additive, backward-compatible patch to `base.html`'s shared mobile `fit()` so its summary-column-width math accounts for the new Skins column when present — verified it's a no-op on every other page that uses `.scorecard-table` (`enter.html`, `view.html`), which never render one.

**New Skins checkbox column**, mirroring GLT's own Skins column but deliberately simplified per @user ("we can remove granularity and friction... should just show a checkbox"): new league setting **5.04, "All Skins Paid Up Front"** (help text supplied verbatim by @user), gating a checkbox column on both the live-entry and completed scorecard views. Decision point resolved with @user mid-session: the checkbox writes directly into the *existing* `round_skins_participants.paid_in` — the same field the full Skins Setup form (`skins.week_view`) already uses — rather than a new parallel flag, so there's one answer to "is this player in skins this week," never two that can drift apart. New `skins.toggle_paid_in` endpoint auto-creates a minimal `round_skins_settings` row (seeded from the season's `skins_config` defaults) if the week's never been set up, so the checkbox works standalone without an admin ever visiting that form. Not gated by season lock, matching the rest of `skins.py` (only past points/handicaps are locked). Added a live "N / M in Skins" tally badge next to the page title.

**New setting wired through every touchpoint the existing `skins_self_optin_enabled` setting uses** (same pattern, followed exactly rather than improvised): `schema_postgres.sql` + new `add_all_skins_paid_upfront.sql` migration (registered in `init_db.py`'s additive list), `admin.py`'s defaults/parse/UPDATE/INSERT, `league_info.py`'s defaults, `seasons.py`'s season-rollover clone-column list, `setting_help.py` entry, `admin/settings.html` checkbox row.

### Decisions Made
- Native per-table sticky headers (un-hide + `position: sticky` on every group) over a single page-level shared-header restructure — much smaller diff, same visual result, since the headers are always identical in content within one page.
- Skins checkbox writes into the existing `round_skins_participants.paid_in`, auto-creating a `round_skins_settings` row behind the scenes, rather than a new standalone flag — @user's explicit call when presented with the fork.
- Desktop column-fit measured via a temporary auto-layout pass (read the browser's own natural sizing) rather than canvas `measureText` like the mobile `fit()` — avoids hand-modeling every visual element in the name cell (role pill, sub/absent badge, nickname, tee picker), and the iOS quirk that ruled this approach out for mobile doesn't apply at desktop widths.

## 2026-08-21 — Score Entry Side Selector: Same Bug Class, Different UI

*Status: `COMPLETED`*
*Type: `Manual`*

### What Was Done

**@user reported two symptoms on Score Entry (`scores.enter_week`) after the 2026-08-19 Schedule-page side-swap fix**: (1) changing the Side selector and hitting Save threw a "Load failed, continue anyway and save changes?" popup, even on a week nobody had started entering; (2) on Root Beer League week 12 specifically, switching Back → Front and saving left the already-completed round's hole numbers unchanged, and a second Save just flashed "Scheduled date updated" — a field they hadn't touched.

**Root-caused both, reproduced against real Postgres before fixing anything**: Score Entry's "Select Side" dropdown (`#ew-tee`, inside the "Edit Week Settings" panel) is a completely different UI control from the Schedule page's Front/Back selector fixed 2026-08-19 — same underlying bug class, different code path I hadn't touched. `ewOnTeeChange()` was pure client-side navigation (reload with a new `?tee_id=` query param) — it never persisted anything. That only changes what a *not-yet-scored* matchup's editable form defaults to; a completed matchup always renders read-only from its own stored `rounds.tee_id`, which the URL param can't touch. The panel's only actual "Save" button belongs to a wholly separate, unrelated form (Scheduled Date only) — explaining the "Scheduled date updated" flash on the second click: that's genuinely the only thing that button ever saves.

For the "Load failed" popup: reproduced `ewSaveAllForms()`'s exact empty-form POST against a real seeded matchup and it succeeded cleanly (200) — so the popup isn't from a scripted app error. "Load failed" is WebKit/Safari's own generic wording for a failed `fetch()` (as opposed to Chrome's "Failed to fetch"), consistent with @user being a mobile user — most likely an aborted in-flight request from iOS backgrounding/a navigation race, not something fixable in isolation. But `ewSaveAllForms()` was blindly re-POSTing *every* visible matchup's form on every side/course change, including fully untouched ones — pure surface-area for exactly this kind of failure on a week nobody's started. Scoped it: score inputs now mark their form dirty on first edit, and only dirty forms get resubmitted.

**Fix**: new `POST /scores/enter-week/<season_id>/<week_num>/side` (`scores.update_week_side`) — updates `matchups.tee_id` for the week and calls `remap_week_to_tee()` (the exact helper built for the 2026-08-19 Schedule-page fix) for any already-scored round. `ewOnTeeChange()` now submits a hidden form to it instead of just navigating. Validated end-to-end against a fresh ephemeral Postgres instance (7/7 checks): a completed round seeded on the back nine actually moves to the front nine after the POST, hole IDs change, gross scores are preserved — the exact scenario @user described for week 12.

### Decisions Made
- The Schedule page's side selector and Score Entry's side selector are two independent UI entry points to the same underlying problem — fixing one doesn't fix the other. Both now route through the same shared `remap_week_to_tee()` helper rather than duplicating the remap logic a third time.

### Blockers / Issues
- None. Full repro-then-fix-then-reverify cycle against real Postgres, not just static review.

**@user confirmed against real production data, same session: Root Beer League week 12 now correctly shows the front nine after the swap.** Fix closed the loop end-to-end — real Postgres validation, then real production confirmation.

### Pending / Next Session
- The "Load failed" popup's root cause (likely WebKit fetch-abort on navigation race) is mitigated (fewer forms attempt to save) but not eliminated — no report yet of it recurring on a genuinely-edited week; revisit only if @user sees it again.

## 2026-08-13 (continued, later) — Mobile Dark Theme: The Actual Root Cause (Malformed CSS Comment)

*Status: `COMPLETED`*
*Type: `Manual`*

### What Was Done

**The hardcoded-`#fff` fix (above) turned out to be real but insufficient.** @user re-tested and `.ap-tile` — a component that had *never* had a hardcoded color, always correctly written as `background: var(--card-bg, #fff)` — was still rendering light. **Walked @user through Chrome DevTools on desktop** (F12 → device toolbar → narrow viewport → inspect element) since this session has no real device or browser-automation access. Confirmed, in order: still light in Chrome's own mobile emulation (not iOS-specific); an "Empty Cache and Hard Reload" plus unregistering a stray old service worker didn't change anything; the Network tab showed a genuine fresh 57.7KB fetch of `main.css` (matches the real file's Brotli-compressed size, so not a cache/staleness issue); the emulated viewport was a confirmed 430×932 (well under the 768px breakpoint); and — the actual finding — **the `@media (max-width: 768px)` mobile override block was completely absent from Chrome's Elements→Styles panel for `<html>`**, not merely shown-but-not-matching (a neighboring, unrelated `@media (max-width: 640px)` block *did* show up correctly in the same panel, proving DevTools does list matching media-query rules — this one just wasn't there at all).

**Root cause found: a malformed CSS comment silently deleted the entire mobile override from every browser's parsed CSS.** The explanatory comment directly above the `@media` block (`main.css:73-87`) contained `--red*/--orange` in its prose — the `*` immediately followed by `/` forms `*/`, the CSS comment-close token, mid-sentence. CSS comments don't nest; the first `*/` a parser finds closes it, full stop. So the comment actually closed one line early, and everything after — including the real intended `*/` — got parsed as invalid top-level garbage sitting directly in front of the `@media` block, which browsers then dropped entirely rather than partially applying. This explains every previous "clean" check: the deployed file was genuinely byte-correct (curl doesn't parse CSS), caching was genuinely fresh, the viewport genuinely matched — the block just never made it into any browser's actual parsed stylesheet to begin with, on any engine tested (Safari iOS, Chrome iOS, Chrome desktop).

**Fixed** by rewriting that one line to spell out the token names in full instead of using an informal `*`-as-wildcard shorthand, removing every `*` immediately followed by `/` in the comment. Verified with a real character-by-character comment tokenizer over the whole file (confirmed brace-counting alone — what every earlier check relied on — cannot catch this class of bug, since a premature close and a later incidental reopen can net out to a numerically balanced file while still corrupting the region in between). Bumped cache-buster to `?v=20260813e`. Full write-up in Technical Reference's Visual Theme section, including the general lesson: if a `:root`/`@media` block goes fully missing from a browser's own Styles panel (not just non-matching) despite the source clearly containing it, suspect a parse-time error — most likely a malformed comment — before suspecting caching or specificity.

### Decisions Made

## 2026-07-30 — Tee Default Write-Through + Wiki Page + Admin Panel Polish

**Traced the full tee-resolution logic** across all three places a tee gets picked for a player (`enter()` single-matchup entry, `enter_week()` week-batch entry, `print_scorecards()`), to answer @user's question of how the personal-default/override system actually works today and whether it touches scoring. Findings:
- Tee choice is **not** cosmetic — whichever tee actually ends up on a scorecard drives that round's par/handicap-index allocation and therefore net score/points (`_process_scores()`, `scores.py`). The *default/preferred* mechanisms themselves add no scoring adjustment on their own — they only decide which tee gets pre-selected — but the pre-selected tee's own hole data is fully load-bearing once submitted.

- Actual hierarchy today: course default (`courses.default_tee_id`) → player's personal `preferred_tee_name` → matchup-specific override (`matchup_tee_overrides`, from the print-scorecards popover), highest priority. **Only `enter_week()` implements all three tiers.** `enter()` never reads `matchup_tee_overrides`; `print_scorecards()` never reads `preferred_tee_name`. Logged as a known inconsistency (Pending, below) — not fixed this session since it wasn't blocking the actual ask.
