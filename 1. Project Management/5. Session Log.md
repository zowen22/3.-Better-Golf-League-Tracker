## 2026-08-03 (continued, even later) — Import Tool: Critical Postgres Bug Fix + 18-Hole Validation

*Status: `STARTED`*
*Type: `Manual`*

### What Was Done
@user asked to work on the CSV import tool: build on the open "Score import CSV for 18-hole rounds" backlog item (WP3.1) and add a new upload-preview/column-mapping step (GLT-style: per-column field dropdown, row-level include/exclude checkboxes, column removal), reference photo provided (not archived — @user asked not to keep it long-term).

Investigating `migration.py`'s `confirm()` before building the new UI surfaced two real, unrelated production bugs:
1. **Critical**: 5 of the 6 "insert then fetch the new id" call sites (players, teams, matchups, rounds, scorecards — everything except the season-creation branch) called SQLite-only `SELECT last_insert_rowid()` with no Postgres branch, unlike every other such site in the codebase. Since production runs Postgres, **any import that needed to create a new player/team/matchup/round/scorecard crashed outright** — which is most real imports. Fixed with a new `_insert_returning_id()` helper (RETURNING on Postgres, `last_insert_rowid()` on SQLite), applied to all 5 sites.
2. Found while validating fix #1: `hole_scores.hole_id` is `NOT NULL`, but a hole number with no matching row in `holes` (no course/tee selected on the import form, or the selected tee doesn't have that many holes configured) was inserted with `hole_id=NULL` anyway — same crash, different constraint. Now skipped per-hole with one summary error message instead of crashing mid-import.

Validated both fixes for real: spun up a local ephemeral Postgres (portable binary + libxml2 shim + TCP-only, per the existing recipe in this file's own Technical Reference section), loaded `schema_postgres.sql`, ran the actual app via `create_app()` (which auto-seeds the Shankapotamus demo league) through a real Flask test client — `upload` → `preview` → `confirm` with a players.csv and an 18-hole scores.csv (`hole_1`..`hole_18`). Confirmed: no crash, 2 new players inserted, 1 round + 2 scorecards created, each scorecard has exactly 18 `hole_scores` rows (1-18) with correct gross scores. This also answers the open WP3.1 item directly — **the 9-vs-18-hole parsing was never actually the blocker**; `_parse_scores()` already dynamically detects `hole_1..hole_18` / `H1..H18`, it just couldn't reach the database before this fix.

### Decisions Made
- Skip-with-summary-error (not crash, not silently drop) for holes with no resolvable `hole_id` — matches the existing pattern elsewhere in this file for other unresolvable-reference cases (missing player, missing team).

## 2026-07-30 — Tee Default Write-Through + Wiki Page + Admin Panel Polish

*Status: `COMPLETED`*
*Type: `Manual`*

### What Was Done

**Traced the full tee-resolution logic** across all three places a tee gets picked for a player (`enter()` single-matchup entry, `enter_week()` week-batch entry, `print_scorecards()`), to answer @user's question of how the personal-default/override system actually works today and whether it touches scoring. Findings:
- Tee choice is **not** cosmetic — whichever tee actually ends up on a scorecard drives that round's par/handicap-index allocation and therefore net score/points (`_process_scores()`, `scores.py`). The *default/preferred* mechanisms themselves add no scoring adjustment on their own — they only decide which tee gets pre-selected — but the pre-selected tee's own hole data is fully load-bearing once submitted.
- @user recalled a personal → flight → course/league hierarchy from a past session. The "flight" tier was never built — it's a code comment TODO (`scores.py:894-895`, "flight default (TODO: needs flights/divisions schema)"), not implemented anywhere; the two unrelated "flight" concepts that do exist (Skins Flights, A/B pairing designation) have no tee relationship at all.
- Actual hierarchy today: course default (`courses.default_tee_id`) → player's personal `preferred_tee_name` → matchup-specific override (`matchup_tee_overrides`, from the print-scorecards popover), highest priority. **Only `enter_week()` implements all three tiers.** `enter()` never reads `matchup_tee_overrides`; `print_scorecards()` never reads `preferred_tee_name`. Logged as a known inconsistency (Pending, below) — not fixed this session since it wasn't blocking the actual ask.

**Tee choice now "remembered" by default, no checkbox** — reverses this session's own 2026-07-29 decision ("opt-in checkbox, not silent linkage"); @user reconsidered and asked for automatic write-through instead. `print_scorecards_player_update()` now also writes the picked tee straight to that player's `preferred_tee_name` (`scores.py`, right after the `matchup_tee_overrides` upsert), so a tee picked once from the popover becomes what pre-fills at score entry going forward, with no separate save-as-default step. Skipped in two cases, both deliberate: a hybrid pick (`tee_id_2` set) isn't written through, since `preferred_tee_name` is a single value and can't represent a two-tee combo; and a pick made while a substitute is playing that slot (`status != 'playing'`) isn't written through either, since the absent original player didn't make that choice and it shouldn't silently overwrite their own standing default.
