# PM Template Improvement Suggestions

This file captures suggested improvements to the base CLAUDE.md project management template, observed during real project work. It is **not** part of the template itself — it exists only in projects that generate suggestions.

---

## How to Use This File

When a Claude session observes a gap or friction point in the PM structure, it logs a suggestion here instead of modifying CLAUDE.md directly (which is template-sourced and should stay clean).

**To apply these suggestions to the template:**
Hand this file to a separate agent with the instruction: "Apply these suggestions to the CLAUDE.md template and any associated PM file stubs." That agent should treat each suggestion as a discrete change proposal, apply judgment on what to adopt, and update the template accordingly.

## Suggestions

### 1. Clarify Session Start Routine — **[Resolved 2026-08-03]**

**Observed friction:** Step 1 says "Check if project files have been shared" — but files live in the repo, not shared by the user. This creates ambiguity about when to read PM files.

**Suggested change to CLAUDE.md Session Start Routine:**
Replace:
> 1. Check if project files have been shared
> 2. If yes — read all files, confirm current status and next priorities

With:
> 1. Read all `1. Project Management/` files to orient on current status and next priorities

**Resolution note:** CLAUDE.md's live Session Start Routine now reads "Read `3. Work Packages.md`, `5. Session Log.md`, and any open Audits/, Plans/, or Handoffs/ files to establish current state" — not the exact wording proposed above, but the ambiguous "check if shared" friction no longer exists. Superseded, not adopted verbatim (per the 2026-07-31 PM docs audit, finding 2.7).

### 2. Add Memory vs PM Files Rule — **[Resolved 2026-08-03]**

**Observed friction:** Claude's built-in memory system (files outside the repo at `~/.claude/projects/.../memory/`) can duplicate content that belongs in Technical Reference, and those memory files aren't committed to the repo — they get lost.

**Suggested addition to CLAUDE.md Rules:**
```
## Memory vs PM Files
The Claude memory system is for thin cross-session pointers only — not content.
All durable knowledge lives in PM files (committed to the repo):
- Architecture decisions → Decisions Log (2. Project Overview.md)
- Conventions, patterns, gotchas → 4. Technical Reference.md
Memory files should say "see Technical Reference §X" not repeat the content.
```

**Resolution note:** This exact section now exists verbatim as `## Memory vs PM Files` in the live CLAUDE.md.

### 3. Add a Known Issues / Bug Log File

**Observed friction:** Recurring bugs (e.g. tee deduplication showing duplicates across web and iOS) got re-diagnosed in a later session because there was no issue tracker. The Session Log captures fixes but is chronological — not queryable by topic.

**Suggested new PM file:** `6. Known Issues.md` (or `Bug Log.md`)
- Lightweight table: Issue | Status | Fixed In Session | Notes
- Bugs that span sessions or risk regression get logged here
- Closed when fixed; never deleted (mark `[Resolved]`)

---

### 4. Cross-Reference Audit Findings to Work Package Tasks

**Observed friction:** CLAUDE.md lists open audits but findings aren't linked to specific WP task IDs. When a finding gets fixed, there's no clear path to mark it resolved in the audit file — the two systems drift out of sync.

**Suggested addition to Rules:**
```
- Each audit finding should reference a WP task ID (e.g. "WP5.3-P2")
- Closing the WP task → mark the audit finding [Fixed] in the same session
```

### 5. Archive Old Session Log Entries — **[Implemented in this project 2026-08-03, CLAUDE.md rule adoption still pending]**

**Observed friction:** Session Log grows unbounded. After many sessions it becomes slow to read at session start and noisy.

**Suggested addition to Rules:**
```
- Keep only the last 5 sessions in 5. Session Log.md
- Archive older entries to 5. Session Log Archive.md
- Archive at session end when log exceeds ~10 sessions
```

**Implementation note (2026-08-03):** Applied to this project — `5. Session Log.md` had grown to 4,042 lines / 128 session headers, well past the ~10-session threshold this suggestion names. Moved every session older than the 5 most recent (everything before 2026-07-29) to a new `5. Session Log Archive.md`, newest-first, same format; left a pointer line at the bottom of the live file. The CLAUDE.md rule addition itself is still just proposed here, not adopted into the template — see "How to Use This File" above for the adoption process.

### 6. Track iOS / Client Work in Work Packages

**Observed friction:** iOS feature parity tasks were called out in Session Log "What's Next" notes but never added to Work Packages. They became invisible to the WP progress tracker and easy to miss at session start.

**Suggested addition to Rules:**
```
- Any "What's Next" item in the Session Log must have a corresponding WP task
  created before the session is marked COMPLETED
- Cross-platform work (iOS, web, API) should be explicit separate tasks, not bundled
```

### 8. Check available MCP connectors before declaring a task blocked

**Observed friction (2026-08-03):** @user asked for a live-production action (recalculate a contest across all weeks on the deployed Buckeye League site). I concluded this was impossible — the Bash sandbox's network allowlist is restricted to `github.com`, so I have no route to the production Render URL — and told the user so. @user then pointed out this project has a `claude.ai Supabase` MCP connector (already authenticated, direct access to the production Postgres project) and Render MCP connectors, all listed in the very first system-reminder of the session as available deferred tools. I had seen the tool names and never checked them, because "no Bash network access" and "no way to reach production" aren't the same claim, but I'd silently treated them as equivalent.

**Root cause:** MCP tool connections are a separate channel from the Bash sandbox's subprocess network egress — a sandbox network restriction says nothing about what an MCP connector can reach, since those calls are host-mediated, not made from inside the sandboxed shell. I only scanned for "can I curl/reach this" and never asked "is there a connector for this."

**Suggested addition to CLAUDE.md Rules:**
```
- Before telling the user a task is impossible due to "no access" / "sandboxed" /
  "can't reach X" — check the available/deferred tool list (ToolSearch, or the
  session's own tool listing) for an MCP connector that might already provide that
  access. A Bash network restriction only describes what the sandboxed shell can
  reach; it says nothing about what a connected MCP server (Supabase, Render, etc.)
  can reach on the user's behalf. Don't conflate "my shell can't get there" with
  "there is no way to get there."
```

This is really a general Claude Code tool-discovery habit rather than something specific to this project's PM structure — also saved as a durable cross-session memory (feedback type), which is more likely to actually get read next time than a CLAUDE.md rule buried in a per-project file.

### 9. CLAUDE.md's "Framework Structure" list is stale relative to CLAUDE.md's own other sections

**Observed friction (2026-07-31 PM docs audit, finding 1.1):** CLAUDE.md's "Framework Structure" section documents exactly 5 numbered files (`1. Problem Statement.md` through `5. Session Log.md`). This project has grown two more top-level files not mentioned there at all — `6. PM Template Improvement Suggestions.md` and `7. GLT Feature Parity.md` — plus an `Orchestration/` folder and an `Artifacts/` folder. All four are real and load-bearing: files 6/7 are actively maintained and referenced by name elsewhere in CLAUDE.md (the "PM Improvement Suggestions" and "Orchestration Handoffs" sections each name their own folder/file directly), so this isn't unused growth someone forgot to clean up — it's CLAUDE.md's own "Framework Structure" list not being kept in sync with CLAUDE.md's other sections as the project grew past the original 5-file template.

**Suggested addition to CLAUDE.md's Framework Structure section:**
```
Projects may grow additional numbered files beyond the base 5 as real needs
arise (e.g. a template-improvement log, a feature-parity tracker) — see this
project's own numbered files above 5, if any, and the sections elsewhere in
this document that reference them by name. Supporting folders alongside
`1. Project Management/` (Audits/, Plans/, Handoffs/, Orchestration/,
Artifacts/) are documented in their own CLAUDE.md sections and/or their own
README.md, not repeated here.
```

Logged here per this file's own rule (see "How to Use This File" above) rather than edited directly into CLAUDE.md, since CLAUDE.md is template-sourced.

### 10. CLAUDE.md should say pushes happen automatically, not just commits

**Observed friction (2026-08-05):** CLAUDE.md's Session End Routine ends with "Remind user to commit and push changes to GitHub" — phrased as a reminder to the user, implying Claude asks/waits before pushing. @user has said explicitly (independently of this project, as a standing cross-session preference) that they want every commit pushed immediately, no confirmation step — "I prefer pushes over asking."

**Suggested change to CLAUDE.md Session End Routine:**
Replace:
> 6. Remind user to commit and push changes to GitHub

With:
> 6. Commit and push changes to GitHub directly — do not wait for confirmation before pushing (only pause if the push itself fails or looks destructive, e.g. force-push/history rewrite)

Logged here per this file's own rule rather than edited directly into CLAUDE.md. Also already captured as a durable cross-session memory (feedback type) — see `~/.claude/projects/-home-zowen22/memory/feedback-always-push.md`.

### 11. Checking the deferred-tools list isn't enough — project-scoped API-key MCP servers can exist without ever being surfaced as available tools

**Observed friction (2026-08-08):** @user asked me to check whether Render's production env vars already had the real Stripe credentials set. I did the right first move per Suggestion #8 above — checked the deferred-tools list via ToolSearch instead of assuming no access — and found two Render MCP connectors (`claude.ai Render`, `claude.ai render_mcp`), both OAuth-based and requiring the user to run `/mcp` to authenticate. I reported that back as the only path. @user then said "I think you should have api keys or something? I think Render isn't connected via oauth" — prompting me to read `~/.claude.json` directly, where I found a **third** Render connector, `render-api`, configured specifically under this project's path (`projects."/home/zowen22/projects/BetterGolfLeagueTracker".mcpServers`) with an API-key `Authorization: Bearer` header pointed straight at `https://mcp.render.com/mcp` — no OAuth needed at all. This connector was never listed in the session's deferred-tools system-reminder and ToolSearch never surfaced it, even when queried directly for "Render."

**Root cause:** Claude Code supports at least two independent ways an MCP server can be attached — account-level OAuth connectors (surfaced automatically as deferred tools every session) and project-scoped connectors defined directly in `~/.claude.json` under that project's path (which, at least for this background-job session, were **not** auto-loaded into the active/deferred tool set). ToolSearch and the system-reminder's tool listing only reflect what the harness actually wired up for the current session — they are not a complete inventory of every MCP server the user has ever configured for a project. I have no visibility into `~/.claude.json`'s per-project `mcpServers` blocks unless I go read that file directly, which isn't something the standard tool-discovery workflow (ToolSearch, deferred-tools reminder) would ever prompt me to do on its own.

**Suggested addition to CLAUDE.md Rules** (or the general Claude Code tool-discovery guidance, since like Suggestion #8 this isn't specific to this project's PM structure):
```
- If ToolSearch/the deferred-tools listing shows only an OAuth-gated connector for
  a service, and the user pushes back that a non-OAuth (API-key) connector should
  already exist — check `~/.claude.json`'s `projects."<cwd>".mcpServers` block
  directly before concluding OAuth is the only path. Project-scoped API-key MCP
  servers can be configured there without ever being surfaced as an active/deferred
  tool for a given session.
```

**Postscript, same session:** even after finding the `render-api` key and hitting Render's real REST API with it (`GET /v1/owners`), it returned `401 Unauthorized` — a genuine response from Render, not a sandbox block (confirmed reachable, just rejected). So the stored key itself is expired/invalid; this still didn't answer @user's original question about the live env vars. Flagged back to @user rather than assumed fixable — a stale/expired project-scoped credential is a separate problem from "which connector exists."

Also saved as a durable cross-session memory (feedback type) — see `~/.claude/projects/-home-zowen22/memory/feedback-check-claude-json-for-api-key-mcp.md`.
